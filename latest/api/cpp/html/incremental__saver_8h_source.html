70// THREADING CONTRACT
71// ------------------
72// The saver's internal state (change tables, dedup map, baseline fields, requires_full_save,
73// is_tracking, counters, config) is serialised by an internal recursive change_mutex, so
74// RECORDING (via GaussianData setters, under data_rwlock) and SAVING (save_changes) may run
75// concurrently: the common case -- a worker thread editing while the main thread saves -- is
76// thread-safe.
77//
78// However, load_and_apply_changes() and create_baseline() deserialise a delta INTO / serialise
79// a baseline FROM the WHOLE attached GaussianData. Those whole-object operations are NOT atomic
80// w.r.t. concurrent edits of the SAME GaussianData, and the saver cannot make them so (it does
81// not own data_rwlock, and holding it across a full apply would deadlock the record path). The
82// CALLER must therefore ensure EXCLUSIVE access to the GaussianData for the duration of
83// load_and_apply_changes()/create_baseline() -- i.e. quiesce other edits to that data -- exactly
84// as one would not deserialise into an object being mutated elsewhere. Only ONE
85// load_and_apply_changes() may run per saver at a time. create_baseline() additionally fails
86// closed (via content_revision) if it detects the data changed under it, so a stray edit is not
87// silently dropped; a structural replace racing the serializer's raw-storage read is a separate,
88// pre-existing serializer concern tracked in its own issue.
