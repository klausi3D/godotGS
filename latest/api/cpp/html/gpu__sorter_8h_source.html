4// =============================================================================
5// GPU Sorting Algorithms
6// =============================================================================
7// Three sorting backends are provided. Each targets a different sweet-spot on
8// the latency/throughput/capability curve:
9//
10// 1. BitonicSort - O(n log^2 n) parallel comparison sort.
11// - Simple, reliable, no auxiliary memory beyond the input buffers.
12// - Best for small datasets (< ~64 K elements) where launch overhead
13// dominates and the extra passes are negligible.
14// - Does NOT support indirect dispatch (element count must be known on CPU).
15//
16// 2. RadixSort - O(n) linear-time 4/8-bit radix sort. ** RECOMMENDED DEFAULT **
17// - Supports indirect dispatch (GPU-driven element count).
18// - Supports 64-bit sort keys.
19// - Best general-purpose choice: high throughput, pipelined, indirect-capable.
20// - GPUSorterFactory::ALGORITHM_AUTO selects this for most workloads.
21//
22// 3. OneSweepSort - O(n) single-pass radix sort with chained decoupled look-back.
23// - Lowest theoretical constant factor for very large datasets (> 1 M).
24// - Does NOT support indirect dispatch (lacks GPU-driven element count path).
25// - More complex; requires chained-scan buffer and careful tuning.
26// - Prefer RadixSort unless benchmarks prove OneSweep is faster for the
27// target workload and indirect dispatch is not required.
28//
29// Use GPUSorterFactory to create instances. ALGORITHM_AUTO will probe device
30// capabilities and fall back through RadixSort -> BitonicSort as needed.
31// =============================================================================

526 // built-in fallback used when project settings are unavailable, and are the
