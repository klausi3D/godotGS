    ADR: Review and merge policy as practised¶

    • Status: Accepted, 2026-11-10 — decided by the owner on that date; the owner's confirming comment on this PR and its merge confirm the recorded text (see Confirmation below).
    • Date: 2026-11-10.
    • Risk: this document is R0 (docs/**), as are the two governance edits that land with it. It changes no code, workflow, branch-protection setting, guard, threshold or gate.
    • Refs: audit findings J-14 and G-04; owner decision D-7; cleanup-plan task CLN-D07.
    • Related: Review policy, Agentic engineering, GitHub settings, Phase-1 guard hardening §3 (the earlier R3 disposition for a sole collaborator).
    • Verified against: b58bbe35d1f (origin/master). Every file claim below was read at that commit.

    Problem¶

    The written review policy asks for more than the repository does.

    • The R3 row of the risk-class table in Agentic engineering gave R3, before this record, the process "ADR before implementation + two reviews + CODEOWNER and human approval". .agentic/policy.json lists "Two independent reviews and CODEOWNER + human approval." under risk_classes.R3.evidence_requirements, and the header comment of .github/CODEOWNERS says "That rule stands; GitHub does not enforce it."
    • Branch protection requires 0 approving reviews and no code-owner review (GitHub settings, the live-state table for master). The "Repository enforcement" section of Review policy already says the R3 two-review rule is "upheld by reviewers and the merging human, not by GitHub".
    • Audit finding J-14 (audit base 1cfcf3c1ccb) sampled 14 merged PRs (#1392, #1391, #1388, #1386, #1381, #1380, #1378, #1377, #1373, #1372, #1369, #1368, #1365, #1361). All were authored and merged by the repository owner's account. The only second party was the Codex bot, whose review state was COMMENTED, never APPROVED. Five of the 14 had no review at all, among them the R3 PRs #1386, #1373 and #1365 and the R2 PR #1392.
    • Audit finding G-04 records the consequence on the check side: only agentic-pr-gate and docs-build are required, so engine correctness is judged by a person at each merge.

    The repository has one human collaborator, so a second human review cannot happen. A written rule that is never met misleads every reader who relies on it.

    Options considered¶

    Option What it is Cost What it enables What it limits
    A. Second human reviewer for R3 Set required_approving_review_count to 1 and turn on code-owner review. Needs a second human with write access; until one exists, every R3 PR blocks. A maintainer, not an agent, changes branch protection. GitHub enforces the R3 review rule; an R3 PR with no approving reviewer cannot merge. Throughput on R3 depends on a person who does not exist today.
    B. Write down the real policy Agent author, independent agent reviewers, owner merges or delegates the merge on green CI; drop the two-review claim. No setting changes. The R3 review rule stays process-only, as it is today. The text matches what happens, so readers and agents stop citing a rule nobody meets. No mechanical stop for an R3 PR that merges without review.

    The audit recommended B now and A when a second human joins.

    Owner decision¶

    • Chosen: Option B, write down the real policy.
    • Decided by: the repository owner, 2026-11-10.
    • Accepted: from 2026-11-10, the date of the owner's decision. This ADR records the answer; no separate owner comment or issue records it.
    • Confirmation: the pull request that adds this ADR is opened from the owner's account (klausi3D), as every agent PR here is, and GitHub does not let a PR's author approve it (see "Require review from Code Owners" in GitHub settings), so an APPROVED review cannot be obtained. The confirmation is the one practised for the owner's OK: a comment on that pull request, posted from klausi3D, stating that the owner confirms the recorded text matches the decision, followed by the merge of that pull request by klausi3D, done by the owner or by the coordinating agent under the owner's merge delegation. Agents use the same account, so GitHub cannot tell the owner's comment from an agent's; the comment says whether the owner posted it or it quotes the OK the owner gave the coordinating agent. The verifier checks them with gh pr view <PR> --json comments (the confirming comment by klausi3D) and gh pr view <PR> --json mergedBy (merged by klausi3D), and pastes both outputs into the pull request.

    The policy, as the owner stated it:

    1. An agent authors the change.
    2. Independent agent reviewers review it: Claude and Codex.
    3. The owner merges, or delegates the merge once CI is fully green.
    4. R2 and R3 changes need the owner's OK.
    5. The two-human-review claim is dropped until a second human joins.

    What this changes and what it keeps¶

    Changed in this PR¶

    • Review policy states the policy above in one sentence, and its "Repository enforcement" section no longer names an R3 two-review rule.
    • Agentic engineering: the R2 and R3 rows of the risk-class table and the "Process only" list state the owner's OK for R2 and R3 and the agent reviews, in place of "two reviews + CODEOWNER and human approval".

    Kept unchanged¶

    • No check is weakened. No required check, branch-protection setting, guard, threshold or baseline changes. The two-review and CODEOWNER rule was never enforced (see the live-state table in GitHub settings); this record moves the text to match the settings, not the settings to match a looser text.
    • Which layers are process-only. As before, the review layers (correctness, domain and human disposition) are upheld by reviewers and the merging human, not by GitHub.
    • Compensating control for R3 PRs with no human reviewer. The owner chose the owner's OK on every R2 and R3 change, on top of the agent reviews. It is a process control: nothing in GitHub enforces it.
    • No voting, and blockers stay open. docs/governance/review-policy.md ("No voting") still holds: a well-founded blocker stays open until it is fixed or a human waives it with a written reason.

    Cleanup-plan process rule (CR-11, not part of the D-7 answer)¶

    This rule comes from the cleanup plan (its review finding CR-11), not from the owner's D-7 answer. It is not existing policy: docs/governance/review-policy.md does not yet state a review-round budget. It applies to cleanup-plan tasks only.

    • The review budget for a cleanup-plan task is three rounds.
    • When the budget runs out with a blocker or an unmet acceptance criterion still open, the task goes to the owner. Nothing is moved to an issue automatically.
    • Only findings the owner dispositions as non-blockers become follow-up issues.

    Consequences¶

    • J-14's required action "an R3 PR with no reviewer cannot merge" is not met under Option B. The agent reviews and the owner's OK are the controls, and both are process. J-14 is closed by the text and the settings agreeing, not by a new mechanical stop.
    • G-04 is unchanged by this record: the set of required checks is a separate question.
    • When a second human with write access joins, Option A becomes available. Adopting it needs a new decision, a branch-protection change applied by a maintainer, and an update to GitHub settings.
    • Cleanup-plan tasks CLN-MS02 and CLN-MS03 depend on this record and may start once it is merged.
