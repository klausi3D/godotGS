    ADR: v1.0 platform and graphics-API targets — Vulkan on Windows and Linux, NVIDIA and AMD¶

    • Status: Accepted on 2026-11-10, when the owner decided it; the owner's confirming comment on the PR that adds this record and its merge confirm the recorded text (see Owner decision).
    • Date: 2026-11-10.
    • Decision: D-3 of the 2026-11 cleanup audit. Task CLN-D03. Bundled with Reference parity at default settings (D-4); the two decisions are independent.
    • Risk: this document is R0 (docs/**). It changes no code, build option, workflow, threshold or gate. The CI lanes it calls for are separate tasks (Follow-up tasks).
    • Refs: #596, #1160.
    • Base: b58bbe35d1f (origin/master). Every source citation below was read at that commit. Paths are relative to the repository root.

    Problem¶

    Release Acceptance Bar §2 lists a v1.0 rung per operating system but names no graphics API and no GPU vendor. The module builds for Windows, Linux and macOS (SUPPORTED_PLATFORMS = {"linuxbsd", "windows", "macos"} in modules/gaussian_splatting/config.py). Its compute paths have run only on Vulkan, and nothing records whether D3D12 or Metal belongs in v1.0.

    No CI workflow targets a second GPU vendor. The self-hosted GPU jobs target Linux runners, for example the gpu-tests job in .github/workflows/baseline_qa.yml (runs-on: [self-hosted, Linux, X64, gpu]) and the prime-world-cache job in .github/workflows/beyond_vram_flythrough.yml ([..., gpu, rtx3080]). The one Windows GPU job, export_smoke_windows in .github/workflows/release_builds.yml, is skipped unless the repository variable GODOTGS_WINDOWS_GPU_RUNNER is 'true' (the job's if:). That variable is not set, and the only registered runners are two Linux machines, ci-cpu-1 and gpu-linux-3080 (read with gh api on 2026-11-10). So CI has no Windows GPU lane for any vendor. When export_smoke_windows does run, it already renders with Vulkan: it calls tests/runtime/run_export_smoke.py, which launches the export in the runtime harness's gpu-vulkan mode (--rendering-driver vulkan), and the export preset disables D3D12 (application/export_d3d12=0 in tests/runtime/export_smoke_preset.cfg.in). The d3d12 entry in its runs-on list is a label from the runner inventory, not a driver choice. No workflow targets an AMD, Intel or Apple runner (audit finding B-06).

    The code has vendor-sensitive constructs that no CI lane exercises. When the subgroup size is 32 or more, the radix scatter in modules/gaussian_splatting/renderer/gpu_sorter.cpp takes a ballot branch (the scatter's gl_SubgroupSize >= 32u branch). That branch assumes contiguous lane-to-subgroup mapping (subgroup_index = lid / gl_SubgroupSize; audit finding B-05). Subgroups smaller than 32 fall back to a per-invocation bitmask indexed by the local ID, which does not use that mapping. Vulkan does not guarantee the contiguous mapping without subgroup-size control, and a mis-ranked scatter produces a wrong sort with no error.

    Options considered¶

    These are the options in the audit's decision list (D-3).

    Option A — Windows Vulkan only, NVIDIA and AMD validated¶

    • Cost: one extra GPU lane, on AMD hardware. The audit's cost assumed an existing Windows NVIDIA lane. None exists (Problem), so Windows validation also needs a Windows GPU runner and lane.
    • Enables: cross-vendor sort correctness (B-05) is tested; one API keeps one set of compute assumptions.
    • Limits: Linux is not a v1.0 target; no D3D12, Metal, mobile or web.

    Option B — add D3D12¶

    • Cost: Godot supports D3D12, but the module's compute paths and subgroup assumptions are untested there; a D3D12 GPU lane and a pass over every compute shader.
    • Enables: Windows users on the D3D12 driver.
    • Limits: a second API adds a second compute-correctness surface before the first is validated on two vendors.

    Option C — add Metal and macOS¶

    • Cost: macOS is only build-supported today, and Apple GPUs need the sort's forward-progress assumptions removed; an Apple GPU lane.
    • Enables: macOS as a target platform.
    • Limits: v1.0 waits on the sort rework.

    Recommendation¶

    The audit recommended Option A for v1.0, stated in the bar: an AMD card in CI costs less than any of the sort-correctness risks it would expose. Only the first game should drive B and C.

    Owner decision¶

    Vulkan on Windows and Linux, validated on NVIDIA and AMD, decided by the owner on 2026-11-10. D3D12, Metal, mobile, web and XR are out of v1.0.

    This differs from the recommendation: it is Option A widened to Linux. Options B and C are rejected for v1.0 for the reasons in Options considered. Adding Linux means AMD validation has to cover Linux as well as Windows, and the bar's existing Linux requirements (Consequences) stay. CLN-EV12-2's contract defines one AMD lane with baseline_qa.yml's harness arguments and does not cover Windows, so the Windows lane is a separate follow-up (Follow-up tasks).

    The decision was accepted when the owner made it. Confirmation: the pull request that adds this record, #1400, was opened from the owner's account (klausi3D), as every agent PR here is, and GitHub does not let a PR's author approve it (see "Require review from Code Owners" in GitHub settings), so an approving review cannot be obtained. The confirmation is the one practised for the owner's OK (Review and merge policy as practised): a comment on #1400, posted from klausi3D on 2026-11-10 by the coordinating agent, quotes the owner's OK given in the coordination session that day (“ja ich stimme den adrs zu. so machen wir es erstmal.”) and states that the owner confirms the recorded text of decisions D-1 to D-8 matches the decisions; klausi3D then merged #1400 (27afe1d1af9). There is no separate issue comment.

    Decision¶

    Platform Graphics API GPU vendors validated for v1.0 In v1.0
    Windows Vulkan NVIDIA, AMD yes
    Linux Vulkan NVIDIA, AMD yes
    macOS — — no; the module still builds (build-supported)
    D3D12 (Windows) — — no
    Mobile, web — — no
    XR / multiview — — no

    The rungs in the release bar (Windows production-tested, Linux editor-tested) are unchanged. The owner did not change them; see Open questions for the owner.

    Consequences¶

    For the codebase and CI¶

    • An AMD GPU lane is a v1.0 requirement. It does not exist yet. CLN-EV12-2 creates it, inert and visibly skipped until an AMD runner is registered. It needs AMD runner hardware, which the owner has to provide.
    • Windows validation (NVIDIA and AMD) needs a Windows Vulkan GPU harness lane and a Windows GPU runner. Neither exists today (Problem). No CLN task creates the lane: CLN-EV12-2 does not cover Windows. A to-file item creates it, inert and visibly skipped until a Windows GPU runner is registered (Follow-up tasks). The existing export_smoke_windows job in .github/workflows/release_builds.yml is an export smoke test, not that lane. It already runs Vulkan, so the decision needs no change to it.
    • No code changes in this record. SUPPORTED_PLATFORMS keeps macos; whether the macOS build stays supported after v1.0 scoping is open (Open questions for the owner).
    • The Linux requirements already in the bar stay: Linux at editor-tested needs the qa and sorting categories on a GPU-backed Linux lane. CLN-SH05 proves and pins those lanes.

    B-06 → CLN-EV12, CLN-EV12-1, CLN-EV12-2 Unblocked and committed: forced-variation batches and the AMD lane.
    CLN-SH05 (#596) Unblocked: prove and pin the Linux GPU lanes.
    Windows Vulkan GPU harness lane Required; no CLN task owns it. Filed from this record (Follow-up tasks).
    CLN-ST05 Unblocked: GPU-tier presets and runtime tier detection, for the two vendors above.
    CLN-LT09, CLN-LT09-1 to CLN-LT09-4 (#1160) Void: XR is out of v1.0. This record and bar §2 carry the XR exclusion that CLN-LT09-1 offered as its alternative.

    D3D12 and Metal rows Out of v1.0. The compatibility matrix gains no row for them.
    Runner hardware An AMD GPU runner and a Windows GPU runner. No D3D12-only or Apple runner is needed for v1.0.

    What stays the same¶

    • The Compatibility Matrix records current evidence, not targets. It is generated from docs/reference/compatibility_sources.yaml and is not edited here; no row is promoted.
    • No threshold, gate or workflow changes.

    Follow-up tasks¶

    • CLN-EV12-1 and CLN-EV12-2: forced-variation batches and the AMD lane.
    • CLN-SO02: subgroup-size-independent radix scatter.
    • CLN-SH05: Linux GPU lanes for qa and sorting.
    • to-file: register an AMD GPU runner (hardware; owner).
    • to-file: register a Windows GPU runner (hardware; owner).
    • to-file: Windows Vulkan GPU harness lane running the REQUIRED batches, on NVIDIA and then AMD; inert and visibly skipped until a Windows GPU runner is registered. Required by this decision.
    • to-file (optional, nit): rename the d3d12 runner label used by export_smoke_windows and listed in the runner inventory (.github/workflows/README.md). The job already runs Vulkan; the rename is cosmetic and not required by this decision.

    Out of scope¶

    • Any code, build or workflow change; each task in Follow-up tasks cites this record.
    • Which AMD and NVIDIA models count as validated, and driver versions.
    • Performance targets per vendor.
    • Platforms after v1.0. This record does not decide how D3D12, Metal, mobile, web or XR would be added later.

    Open questions for the owner¶

    1. The Linux v1.0 rung: the bar keeps editor-tested. Does "validated on NVIDIA and AMD" raise it to production-tested like Windows?
    2. macOS: keep macos in SUPPORTED_PLATFORMS as an unvalidated build, or drop it.
    3. When the AMD runner is expected, so that CLN-EV12-2 can move from skipped to required.
